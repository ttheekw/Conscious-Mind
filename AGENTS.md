# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, etc.) working in this repository.

## Project status

**Working prototype.** `cargo run` starts a TUI built like git (the user asked for this in place of "every message is a task", 2026-11-14): there is one **main** conversation that keeps going; what the user says goes to it; when something is a piece of work of its own, main decides to open a **branch**, which works by itself in its own tab and is **merged** back into main when it ends. A **routine** is a job set to repeat or start later; each run of one is a branch too. "Task" below means main or a branch. Each task is given success criteria before it starts and is checked against them when it ends; when the user's response disagrees with the criteria, a learner works out what the user meant. Several branches run at once, each in its own tab that shows what it is doing. A model works on a task as an agent: it has tools (read, list, search, write, edit, shell, plan), every call goes through guardrails, and changes wait for the user's approval. When a task needs facts the harness does not have, it is shown as paused for **knowledge research**: the web is searched, the best pages are read and kept in the local knowledge graph, and later tasks find them by lookup. Around that: per-task model routing with an interpreted, self-rewritten policy; a knowledge graph with conversation memory; a persistent timeline. It writes and reuses its own skills, compacts long tasks, follows the project's own instruction file, can delegate to sub-agents, and can schedule jobs for itself (by time, or when a file or folder changes). The harness runs as a background process (`src/daemon.rs`) that the TUI attaches to, so work and scheduled jobs carry on with the screen closed. Lookups are by words, graph links and meaning (a small embedding model that runs locally). When a task cannot be done because of the harness's own code, it can ask for that code to be changed: the change is worked out in a copy, adopted only through a gate, and the harness restarts into the new build (`src/selfupdate.rs`). Not built yet: carrying on by itself until criteria are met (the goal loop), MCP, schedules triggered by a condition, and starting the background process at login. `--demo` still runs the original scripted feed.

### What exists

- `src/event.rs` — the event schema (`EventKind`). This is meant to become the real event log; the TUI renders only from it. An event is carried with the task it belongs to (`Tagged`; `task` in the timeline file; main is task 0, `live::MAIN`); events about the harness itself belong to none. Task events: `TaskOpened` (origin `you` for main, `main` for a branch, `routine #N`), `Merged` (a branch's result brought into main; carried by main), `TaskUpdate` (`TaskState`: queued, working, researching, done, failed, stopped) and `Research` (a search made, a page read, what was kept).
- `src/app.rs` — TUI state: `App::apply_in` derives harness state from events, per task (`TaskView`: title, state, what it is doing, goal, plan, context, counts); the rest is view state. The header, PLAN and CONTEXT panels describe the task whose tab is open (`shown_task`; on the overview, the newest one still going). Mouse hit-testing uses rects recorded during render in `App::hits`.
- `src/ui.rs` — all rendering. Panels: header (task, state, model, budget/context/plan gauges), AGENTS tree, PLAN, the centre, CONTEXT WINDOW, THROUGHPUT, TOOL CALLS, SIGNALS (pending approvals with clickable accept/deny), input line; modals for tool call, event, context section, agent, help.
  - **The centre is tabs: main, then its branches** (the user asked for tabs by task in place of the fixed TIMELINE / RAW / MEMORY tabs, then for main-and-branches, 2026-11-14). The strip on the top border is `0 MAIN` (the tab a screen opens on: the conversation, what the harness itself says, and each `MERGED` entry with the result the branch brought back), `b BRANCHES n` (the board), then one tab per branch, newest first; `]` `[` step through them. Main never shows as finished: having answered it is `READY`. **Branches that have ended are not listed by default** (the user asked, 2026-11-14): they have no tab and no row on the board, since what they found is merged into main; `e` lists them too and hides them again (`App::show_ended`, `listed_branches`), and the board's summary says how many are hidden. The tab that is open stays listed whatever its state. The board (`render_board`) lists each branch with its state in words and a glyph of its own (never colour alone), how long it has taken, what it is doing now, and what it has used. A task's tab opens with `render_task_head`, which says plainly when the task is **paused for knowledge research** or **waiting for you**, then shows only that task's events. **ACTIVITY is the conversation only** (the user found the step-by-step feed too much, 2026-11-14; `ui::in_conversation`): what was said, what was answered, what a branch merged back, and warnings and errors, rolling with the newest at the bottom. What it is doing right now is the one `now ▸` line at the top of the tab; every step (tool calls, model calls, state changes, criteria) is in RAW EVENTS. Do not add other event kinds to ACTIVITY. What the agent says before taking a step (`Thought`) is a step, not conversation: it shows as a draft while it is written and is then in RAW EVENTS, in main and in a branch alike (the test `a_branch_keeps_what_it_showed_after_a_visit_to_main` pins that nothing a tab showed as an event is lost by visiting another tab). **A reply shows while it is being written** (the user asked, 2026-11-14): the text streamed so far is a *draft* (`Live::drafts`, `ToClient::Draft`, `App::set_draft`), drawn at the bottom of the tab of the task writing it with a `writing` mark and a cursor, and replaced by the finished reply's event. A draft is for the screen only and is never an event or in the timeline; a tool request a model writes out as text (`<tool_call>`) is cut from it. Within a tab, `1` `2` `3` (bottom border) switch between ACTIVITY, RAW EVENTS and KNOWLEDGE (its lookups, research steps, what was learned, and each context that was given to the model with why each part was there).
  - **Input:** `n` always talks to main. `i` replies in the open branch once it has answered, and otherwise talks to main; the chip on the input line says which (`TO MAIN` / `REPLY IN BRANCH #3`) before anything is sent. The screen never jumps to a new branch's tab: its tab appears and the user goes to it. `X` stops what the open tab is doing; `+` `-` rate it. The input line stays open after sending, so leave it with Esc before using other keys.
  - **The MIND panel** (`render_mind`): on the left a map of the real memories the store holds (the newest 40 notes, `Live::shown_memories`), one mark each, shaped by kind (`●` event, `◆` fact, `■` always kept in mind) and fixed in place so it can be clicked; a click, or `m`, opens the memory itself (`Modal::Memory`: its title, kind, how far it is trusted and where it came from, how often it was given to tasks and rated, and its text; `↑↓` step through them). A memory is sent to the screen with that text (`MemoryNode::text` / `about`, built by `live::memory_node`, text cut at 600 characters). On the right: events a minute and the agent's latest stated thought. The confidence, surprise and focus gauges were removed (the user asked, 2026-11-14): only the scripted demo ever fed them. Do not show a gauge the real harness does not feed.
- `src/demo.rs` — scripted run that pauses on an approval gate; approve/deny branches the script. Sends/receives `demo::Command`, which stands in for the future daemon protocol.
- `src/provider/` — the model provider layer. `mod.rs` holds the `Provider` trait (`complete(&Request, on_text) -> Response`), the request/response types, and `from_spec("backend[:model]")`. A provider makes one model call; it never runs tools or keeps conversation state.
  - `openai.rs` — any OpenAI-compatible chat-completions endpoint with SSE streaming and native tool calls. Serves the `openai`, `openrouter` and `local` (llama-server / Ollama) backends. API keys come from the environment, or else from the secrets the user typed into the secret window (`secrets::get`), and are redacted from error text.
  - `claude_code.rs`, `codex.rs` — the Claude Code and Codex CLIs run as subprocesses in **model-only** mode, using the CLI's existing login. They run in an empty temp directory so they see no project files. Claude Code has its tools, MCP servers, settings and session persistence switched off. Codex has no flag to remove its built-in tools, so it runs in a read-only sandbox, is told not to use them, and any use comes back in `Response::warnings`.
  - `cli.rs` — shared subprocess plumbing (timeout watchdog, request flattened to a text transcript). These CLIs take no tool list, so the tools are described in the prompt and the model requests one by writing a `<tool_call>{"name", "arguments"}</tool_call>` block in its reply (`parse_reply`). The CLI is started with no tools of its own. **Do not go back to structured output (`--json-schema` / `--output-schema`) for this:** it gives the model a `StructuredOutput` tool, the model then tries to call the harness's tools natively, and the CLI answers "No such tool available" (seen with Sonnet, 2026-11-14).
  - Every backend checks that a requested tool was actually offered and that its arguments are a JSON object (`check_tool_calls`); full schema validation belongs to the future tool layer.
- `src/router.rs` — per-task model routing. **Only the core model is fixed** (the user names it). Per task: (1) the core rates complexity 1–5 (`COMPLEXITY: <n>` / `WHY:`, plain text parsed leniently so weak models can do it); (2) the interpreted policy script (`policy`) reads the recorded evidence (`learn`) and picks a model family for that level; (3) feedback adds to the evidence; (4) the core periodically reviews the policy and may rewrite it. `Router::choose` never fails: an unreadable or failed rating resolves to the core. `Router::complete` falls back to the core if the chosen model errors and takes that model out of the pool for `COOLDOWN` (10 min, remembered across runs); such failures are about availability and are **not** counted as evidence about capability. Routing costs one small core call per task (plus one more, once, when a backend offers a family whose size tier is unknown and the core has to sort it) and is skipped when only one model is available or with `--no-route`.
  - The pool: at startup `provider::available_models()` asks each backend present. Only the **latest model of each family** is kept (`latest_per_family`: `gpt-6.1-sol` supersedes `gpt-6-sol`), and no model version is named in the code. Codex: its own catalog (`codex debug models`). Local server: `GET /models`. Claude Code: its three family aliases (`haiku` / `sonnet` / `opus`), which the CLI resolves to the latest of each; it has no list command. `~/.config/conscious/models.json` or `CONSCIOUS_MODELS_FILE` replaces the pool with `[{"spec", "good_for", "tier"}]`; that is currently the only way OpenAI / OpenRouter models join it.
- `src/learn.rs` — the recorded routing **evidence**, saved to `~/.local/share/conscious/routing.json` (`CONSCIOUS_KNOWLEDGE_FILE` overrides; **use the override when experimenting** so test feedback does not train the real file). Keyed by family (`codex:gpt-sol`), so it survives version bumps. For each (family, complexity level) it counts good and bad ratings; one rating also counts half for neighbouring levels (success → easier, failure → harder). It records facts only and takes no decisions. Feedback today is the user's verdict (`+` / `-` in the TUI, `conscious feedback good|bad` after `ask`); once the goal loop exists, verified success criteria should feed the same path.
- `src/policy.rs` + `src/policy/default.rhai` — the **interpreted decision policy**. How evidence becomes a choice is a Rhai script (`estimate(c, level)` and `select(level, candidates)`; contract in the script header), not compiled code, so the core model can rewrite it. This is the hybrid split: the script's content may be model-written (non-deterministic), everything around it is deterministic and compiled:
  - *Sandbox* (`sandbox()`): no modules, no `eval`, no I/O, capped operations and sizes. A script only sees the `Facts` passed in; the harness validates that the returned index is one of the offered candidates.
  - *Regression gate* (`check`): a rewrite is adopted with no approval, but only if it is under `MAX_SOURCE_BYTES`, never errors, answers the same twice, keeps the fixed behaviours (trivial task not to the large model, expert task not to the small one, 10 good beats 10 bad, cheaper of two equally proven, ratings move estimates the right way), and scores no worse than the policy in use when replayed against the recorded outcomes. Rejections are remembered and shown to the core at the next review.
  - *Versions and rollback* (`PolicyStore`): each adopted version is `policy/vNNNN.rhai` beside the knowledge file, with `history.json`. A version is rolled back, deterministically, when its file no longer loads, when it errors or returns an invalid index at run time (the previous version answers that same call), or when it gets ≥ 2 bad ratings and more bad than good within its first 6 rated tasks. Rollback goes to the newest earlier version never rolled back, ending at the built-in script (v0), which cannot be rolled back.
  - *Review*: after a bad rating, or every 5 rated tasks, the core is shown the script, the evidence, recent ratings and past failed rewrites, and replies `KEEP` or a new script (`Router::review`). In the TUI this runs on a worker thread; with the CLI it runs at the end of the next `ask`.
  - Guardrails and this gate must stay compiled. Do not move them into a script.
- `src/knowledge/` — the **knowledge store**: a graph the agent retrieves from and writes to (graph-lookup RAG). Stored as one JSON file, `knowledge/graph.json` beside the routing knowledge (so `CONSCIOUS_KNOWLEDGE_FILE` moves it too). No extra dependencies. The rest of the harness uses only `KnowledgeBase` in `mod.rs`. Module boundaries, which must be kept:
  - `graph.rs` — data model and persistence only: nodes (`Document`, `Section`, `Chunk`, `Term`, `Note`), edges (`Contains`, `Next`, `Mentions`, `References`, `Related(label)`), and `Provenance` (source, time, `Trust`) on every node. Must not parse or score text.
  - `ingest.rs` — pure text → sections, passages, the terms a passage names (inline `code` spans in prose, definitions in code) and the paths it points at. Deterministic, so its output is `Trust::Verified`. Must not touch files, the store or a model.
  - `index.rs` — BM25 over node text → scored node ids. Must not know about edges, spaces or trust; the caller passes a filter.
  - `vectors.rs` — the meaning index: a unit vector per passage and note, searched by cosine closeness (brute force) → scored node ids. Kept in `vectors.bin` beside the graph, derived from it and rebuildable. A vector is tied to a fingerprint of the text it was made from and to the model that made it, so changed text is embedded again and a change of model starts afresh. Must not call a model or know about edges, spaces or trust.
  - `embed.rs` — the only part that runs the embedding model (`Embedder` trait; `Local` is `bge-small-en-v1.5`, quantised, through `fastembed`). It runs on this machine: nothing embedded leaves it. Its files (about 65 MB on disk) are downloaded once, on first use, into `~/.cache/conscious/models`. Tests use a stand-in (`embed::testing::Ideas`); `cargo test -- --ignored real_embed` runs the real one.
  - `retrieve.rs` — the lookup: seed from the word index and, when given the question as a vector, from the meaning index too (passages at least `MIN_CLOSENESS` (0.55) close; one found both ways counts for both), spread relevance along edges (weaker per hop and through high-degree nodes, so passages linked to several seeds rise), pack the best passages into a token budget. Pure and deterministic; must not do I/O or call a model.
  - **Two kinds of learned behaviour, each with a limit** (the user asked for this to stop memory bloating, 2026-11-14; the shape follows TextReg, arXiv 2605.21318, which names the failure: learned text that keeps growing and fills with narrow rules that fit one case). A **rule** is how to behave whatever the task, with no knowledge of any one project; **know-how** is what matters again for one kind of task and says when it applies. Reflection (`skills::DISTILL`) must say which, in at most 30 or 60 words, and is told that what matters to one task only is not kept. The harness, not the model, enforces it (`lessons.rs`): what is called a rule but quotes a name, gives a path or a number, or speaks of "this project" is kept as know-how (`looks_specific`); an entry over the length limit is refused, not cut; only so many are in use and the least useful is retired to make room. A rule is put in front of every task (`KnowledgeBase::rules`, the `rules` context section) only once it is confirmed and has enough support behind it, counted as separate tasks that drew the same thing (`Node::drawn_by`) plus runs and ratings that went well with it; only so many rules stand, within `RULES_BUDGET` (600 tokens), best supported first. Until then, and always for know-how, it is found by lookup only when a task is about it. Standing rules answer for every task they are in front of (they are added to each run's `given`). TextReg's parts map as: its sorting of feedback into general rule / case patch / style → rule / know-how / not kept; its RuleBank recurrence count → `drawn_by`; its capacity and scope penalties → the length cap, the count caps and the specificity test. Not taken: rewriting several entries into one more general entry.
  - **Two kinds of memory, by who may see them** (`lessons::Privacy`, `KnowledgeBase::privacy`; the user set this out, 2026-11-15, after their own name was found in this public repository). (1) **About the user and what they want**: who they are, how they like things done, what they meant (`Intent`), know-how from their work, every remembered fact and event. This is **private**: it stays in the data folder on their machine and is in nothing exported or published. (2) **How the system itself works to solve a problem, whatever the request**: a rule the agent drew for itself. This is **shareable**, but only once it is confirmed, still in use, and names no project, file, value (`looks_specific`) or person (`speaks_of_someone`). Everything is private unless it is plainly of the second kind. `conscious lessons` says which each is; `conscious lessons export` prints the shareable rules and nothing else (`shareable_rules`); `conscious lessons import FILE` takes rules from another copy as unconfirmed, refusing any that name a project or a person (`import_rules`). The memory window on the screen says which kind a memory is. **Nothing from the data folder is ever committed to this repository**, and the only path out of it for learned text is `export`.
  - **The project's text is not about the user.** Passages found in the project's code, documents or web pages are given to the model with a line saying they describe that material, not the person it is talking to (`KnowledgeBase::render`). Before this, conscious run in its own source folder read a name out of a test and gave it as the user's.
  - `tuning.rs` — **the limits are learned, not picked** (the user: "pick based on what happens, that's learning too. Everything is learnable based on user feedback", 2026-11-14). The support a rule needs (starts 3, stays within 2–6), the rules that may stand (12, 4–20), the lessons in use (150, 50–500), the longest a lesson may be (500 characters, 200–800) and the closeness at which two notes are the same (0.95, 0.90–0.95) each start at a default and are moved by evidence. This is the harness's usual split: *what the value is* is learned; *how it may move* is compiled: a floor and ceiling it can never leave, one step at a time, only on a stated amount of evidence, which is then spent, and no model decides. The rules: 12 tasks in a row going well with standing rules → a rule needs one less; a standing rule retired for doing badly → one more; every rule slot taken and 15 in a row going well → one more slot; tasks with standing rules going badly 15 points more often than tasks without (8 of each) → two fewer slots; a lesson that was doing well having to make room, or one retired for room being learned again (it is then brought back) → room for 20 more; over 60% of lessons never given to any task when room is needed → 10 fewer; long lessons doing 20 points worse than short ones → 50 characters shorter; 3 lessons refused for length while long ones do no worse → 50 longer; the same-bar drops to the lowest closeness at which every pair a model was asked about said the same (5 or more, with one at that very step) and goes back up when a pair that close says different things. "Went well / badly" is the user's rating or the run's own checks (`KnowledgeBase::task_went`, `learn_from`). Every move is kept with its reason (`tuning.json`), said in the timeline ("Learned from what happened: …"), and listed by `conscious tuning`. **When adding a limit or threshold to this project, give it bounds and an evidence rule here rather than a fixed number**, unless it is a guardrail: guardrails and the bounds themselves stay compiled. Not yet learned this way: the lookup's closeness floor and token budget, the idle pass's budgets, the number of tasks that run at once, and the skill-retirement thresholds.
  - **An exchange with nothing in it is not filed** (`MemoryKind::Nothing`): when the model that reads an exchange finds a greeting, thanks or small talk, it is left out of the knowledge graph. It is still in the timeline, which keeps everything. An old unread memory found to be nothing is retired.
  - `lessons.rs` — **how the agent's own lessons earn their place**, and how memory is kept free of repeats (added after research into self-improving context: ACE, Dynamic Cheatsheet, the experience-following study, sleep-time compute; 2026-11-14). All fixed rules, no model: a lesson starts unconfirmed (`Trust::Inferred`, and anything unconfirmed starts a lookup with 0.8 of the weight); the user's rating of a task counts for every lesson that task was given (`given`, recorded in the node's `Record`) and for the lessons it wrote (`rate_lessons`); a good rating confirms (`Trust::Experience`), a bad one retires an unconfirmed lesson at once and a confirmed one at 2 bad with more bad than good; a run that did not finish cannot vouch for its own lesson; a run's own checks count without waiting for a rating (`judge_outcome`, fed by `agent::Outcome`): a verified run confirms the lessons it used and wrote, a failed one counts against those it used, and an unconfirmed lesson is retired after 2 failed runs with nothing ever in its favour; the user's word outweighs checks (a lesson no rating of theirs has backed is retired by one bad rating); a lesson saying what one already held says is not stored (`add_lesson` → `Kept::Known`); `merge_repeats` merges notes of the same kind that say the same (the newest stands, or for lessons the best record). Retired nodes stay in the graph with the reason (`Node::retired`) and are never found again. "Says the same" is equal text once case and punctuation are set aside, or closeness ≥ `SAME` (0.95): measured with the model in use, rewordings score 0.93–0.97 but opposite statements on one subject reach 0.925, so the bar is deliberately above that. Pairs between `NEAR` (0.90) and `SAME` are not decided by closeness: in idle time a model is asked whether they say the same (`near_repeats`, `extract::same_statement`, `settle_pair`), and a "different" is remembered on the node (`apart`) so the pair is not asked about again. Memories that gather on one subject (`related_groups`: 4 to 8 remembered facts or events at least `RELATED` (0.70) close to the first) get one summary written by a model (`extract::summarise`, `add_summary`): a new unconfirmed memory linked to the ones it was made from, which are all kept; a group the model finds is not one subject leaves a retired marker so it is not tried again.
  - `extract.rs` — the only part that calls a model: optional relation extraction (`subject | relation | object`), always recorded as `Trust::Inferred`, and only as edges between terms.
  - `cli.rs` — `conscious knowledge ingest|search|add|stats`.
  - **Lookup boundaries** are the fields of `Query` and are hard limits: `spaces` (namespaces; a lookup never returns or walks through a node outside them, and terms are per space, so spaces are not connected), `min_trust` (`Inferred` < `Experience` < `Verified`; lower nodes and edges are ignored), `max_hops`, `max_results`, `token_budget`. Each hit says why it was found (matched words, or the link it was reached over).
  - **Seeing a lookup:** each lookup is one `KnowledgeLookup` event carrying, per passage, the route it was reached by (`Hit::path`: the node whose words matched, then each link followed). In the TUI, `g` (or Enter on the LOOKUP line) opens the lookup view (`ui::render_lookup`, `Modal::Lookup`): the question and searched words, the funnel (matched → reached → given to the model), then the routes drawn as one node-and-link graph (`ui::lookup_graph`: question on the left, nodes in columns by distance, passages given to the model ringed and numbered, the selected route lit with a pulse running along it), drawn with solid box-drawing lines that turn with rounded corners and merge where routes share a stretch (`ui::draw_lookup_graph`; the user asked for continuous lines, not braille dots), and underneath the selected passage in words: its route, why it was found, where it comes from, and the text the model was shown. ↑↓ steps through passages.
  - Retrieved passages are given to the model in a block that states its provenance and marks it as data, not instructions. In live chat each user message triggers a lookup; it appears as a `KnowledgeLookup` event and a `knowledge` section in the `Context` event.
  - **Memory** lives here too. After each answer a small model (`Router::cheapest`) reads the exchange and says what it is before it is stored (`extract::digest`: kind, title, a self-contained summary, key terms). The memory is filed under that meaning, with the exchange itself kept underneath, so it is found by what it means rather than by the words that were typed ("I am X" is found by "what is my name"). If the model cannot be reached the exchange is stored as said, and re-read on a later start (`KnowledgeBase::undigested`, up to 25 per start). Kinds: `identity` and `instruction` are **standing** memories, put in every model call (`KnowledgeBase::standing`, newest 24) and left out of lookups; `fact` and `event` are found by lookup. Working memory is per task: `live.rs` sends only that task's own most recent turns verbatim (`HISTORY_BUDGET`, about 6,000 estimated tokens); older turns, and everything said in other tasks, are not in the request and come back through the lookup when relevant. Exchanges still in a task's working window are excluded from its recall so the model is not shown them twice.
  - **No file names in the UI.** The user asked for the UI to show what is going on, not project files. The memory view lists remembered things (`KnowledgeBase::memories`), never documents. Code passages are titled by what they define (`code: Router, choose`), prose by its heading, and a passage's origin is given in words (`KnowledgeBase::origin`: "the project's code"). Paths are still kept in provenance and given to the model.
  - Web pages read by research are ingested like any prose (`ingest_as`, `Trust::Inferred`, space `research`, source = the page's address).
  - **Lookup by meaning** switches itself on: `Live::start_meaning` loads the model on a background thread at start, then every 2 s embeds whatever has no vector yet (`knowledge::embed_pending`, which never holds the store locked while the model runs). Until the model is ready, or if it cannot be loaded (no network on the very first run), lookups are by words and links and the timeline says so. Each lookup's limits line says which it was ("by words and by meaning" / "by words only"), and a passage found by meaning says how close it was. `--no-semantic` turns it off. `conscious knowledge search` uses it too.
  - **Idle time is used on memory** (`Live::tidy_when_idle`): once nothing has run for 60 s, and at most every 30 minutes: plain repeats are merged (no model); up to 5 near-repeat pairs are put to the cheapest model; up to 10 memories stored before a model had read them are read; up to 2 summaries are written. Those 17 calls are the pass's whole budget. It says what it did only if it did something (`MemoryConsolidated` events and one line). The daemon does not count as settled while a pass runs.
  - Not done yet: summarising old turns; reranking. (The agent does write its own lessons into the store: see `reflect` under agent behaviours.)
- `src/live.rs` — live feed with the same surface as `Demo` (`poll` / `handle` / `throughput`), as **main and its branches**. Every message goes to main (`Command::UserMessage` → `Live::say`; task 0, `MAIN`), which is opened by the first thing ever said and is then always there; `Command::Reply` continues a branch that has answered. Each task runs on its own worker thread with its own conversation (`Task::thread`), is rated and routed, then run by the agent loop (with a `Guard`; without one, as in some tests, it is a single model call).
  - **Who decides to branch:** main, with the `branch` tool (`title`, `task`), which only main is offered (`Hooks::branch`; told what it is by `MAIN_BRIEF`, a branch by `BRANCH_BRIEF`). The decision is the model's, but it is not left to the prompt alone: **main is not offered the tools that change files or hand work on** (`agent::MAIN_LEAVES_TO_BRANCHES`: `write_file`, `edit_file`, `delegate`, `self_update`), so anything that changes the project has to go on a branch and main stays free to talk. (Seen with Sonnet before this rule: it did a whole build job inside main and a question asked meanwhile had to wait.) Main can still read, search, run shell commands the guard allows, recall, research, schedule and plan. A branch starts with nothing from main's conversation but the brief main wrote.
  - **Merging** (`Live::merge`, `merge_note`): when a branch's run ends, its answer is put into main's conversation as a marked note (cut to half of main's working memory if long; all of it is in the branch's tab and in memory) and a `Merged` event is carried by main. A branch that ended with no answer merges a note saying so. A reply in a branch runs it again and merges again. Two user-side messages in a row are joined into one (`push_user`), since some local models only take alternating turns.
  - **What is typed shows at once** (`Live::with_echo_first`, on in the real program): `handle` only announces the message; its context (the knowledge lookup, which takes a moment) is assembled by the next `poll`, after the message has gone to the screens. Tests leave it off, so `handle` returns everything.
  - **Main is never held up by branches:** it has a place of its own outside `MAX_RUNNING`. What is said while main is still answering is shown at once and taken up, together with anything else said meanwhile, as soon as it is free. A turn of main that opened a branch is not judged against success criteria (the branch is, against its own).
  - Fixed rules, compiled: at most `MAX_RUNNING` (3) branches run at once and the rest wait in the order asked (`TaskState::Queued`); a routine's run is a branch like any other and takes a slot; a reply to a branch that has not answered is refused; `Command::Stop` ends a task at its next step and answers a waiting approval with no. A call that needs approval blocks only its own task's thread until `Command::Decide` arrives. A rating (`Command::Feedback { task }`) counts for the model that ran that task (`Router::decision` / `Router::rate`), not for whichever ran last.
  - **Context holds what the task needs, not everything** (the user asked for this, 2026-11-14). A model call is given: the harness's rules; the project's instruction file, whole only if short, otherwise just the blocks that mention the task's words plus the headings left out (`agent::project_instructions` / `relevant_parts`: deterministic word matching, about 6,000 characters); the list of skills; standing memory; the passages the knowledge lookup found for this message; and **this task's own conversation only**. Nothing from other tasks is carried along: it reaches a task through the lookup if it is relevant. Every assembled context is a `Context` event saying what was included and why, shown in the task's KNOWLEDGE view.
- `src/claims.rs` — which task is changing which file. Tasks run side by side in the same folders; the first to change a file with `write_file` / `edit_file` holds it until that task ends (`Live` releases on finish), and another task's change to it is refused before anything is asked of the user, with the model told who holds it and to come back later. Nothing waits, so two tasks cannot block each other for good. What a shell command writes is not covered (it cannot be known in advance).
- `src/selfupdate.rs` — **the harness rewriting its own Rust source, rebuilding and restarting** (the user asked for this, 2026-11-14: when a task's success criteria fail because of the harness's own code, it should rewrite the code, recompile and restart, automatically if the tests pass). The model asks with the `self_update` tool (`problem`, `change`); everything after that is fixed here and in `live::run_self_update`, not left to the model:
  - *A copy.* The source (found through the compile-time `CARGO_MANIFEST_DIR`) is copied to `~/.cache/conscious/selfupdate/work`, build output excluded. The change runs as a task of its own ("Change the harness itself: …", asked by "the harness itself"), in which the model edits the copy with the ordinary tools under `Guard::for_scratch` (confined to the copy; forbidden commands still forbidden). The real source is not touched until adoption. The asking task is told it cannot use the change and must finish.
  - *The gate* (`gate`), run by the harness in the sandbox with no network: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, all `--locked --offline`. Before that, in plain code: something must have changed, **no existing test may be removed or renamed** and **at least one new test must come with the change** (`test_fns` reads `#[test]` functions from the source text). The model's own claim that the tests pass counts for nothing. A refusal is sent back to the model to fix, up to `GATE_ROUNDS` (3).
  - *Protected files* (`PROTECTED`: `guard.rs`, `agent.rs`, `selfupdate.rs`, `policy.rs` and its default script, `knowledge/tuning.rs`, `web.rs`, `daemon.rs`, `Cargo.toml`, `Cargo.lock`, `install.sh`, `build.rs`): nothing is beyond changing, the guardrails included (the user: "even the guardrails should be changeable given user consent"), but a change touching any of them is put to the user as an approval request, **whatever mode the harness is in**, showing the change itself line by line (`diff`), and is dropped if declined. Anything else that passes the gate is adopted with no approval. A tool the guard does not know is denied, so a self-written tool cannot be used until a guard change has been approved.
  - *Adoption* (`adopt`, `install_binary`): the replaced files are backed up under `backups/<n>/`, the changed files are copied into the real source, and the real binary is built there in the sandbox (same profile as the running one; copied over the installed binary if it runs from elsewhere). If that build fails the source is put back.
  - *Restart:* `Live::take_restart` gives the reason once nothing is running; the daemon tells its screens it is restarting, ends, and `main::restart_into_new_build` starts the new build and waits for it to answer. **If it does not come up, the update is taken back (`rollback`) and the previous build is started.** Screens reconnect by themselves (`Remote::reattach`). With `--no-daemon` there is nothing to restart into and the screen says to start again.
  - *Records:* every attempt, with what was asked, what changed and what came of it, is in `history.json` (`conscious selfupdate`); `conscious selfupdate rollback` takes the newest adopted one back. On by default; `--no-self-update` turns it off. In careful mode asking is a high-risk approval; in trusted mode asking is allowed.
  - *It refuses to start* without a working sandbox (code the harness wrote is never built or tested outside one), when another self-update is under way, when the source is no longer on the machine, or with less than `NEEDS_FREE` (6 GB) of disk free (the copy builds every dependency for itself the first time).
  - *Known limits:* the gate cannot tell a weakened assertion from an honest one (only removed or renamed tests are caught); nothing rolls an adopted change back for drawing bad ratings later; the whole path from gate to restart has been tested in parts but **not yet run end to end on a real change** (the session it was built in had no sandbox and too little disk).
- `src/goal.rs` — **success criteria, and learning from how the user responds to them** (the user asked for this, 2026-11-14: "for each task come up with some success metrics; from the user's response know if they were good or bad; if bad, learners should activate to know the user's intent"). Three small calls to the cheapest model, each with a strict reply form and a lenient reader; a reply that cannot be read skips the step and never fails the task:
  - `write`, before the work: 2 to 4 criteria (`MAX_CRITERIA`), written with what memory holds on how this user judges results (standing memory plus the lookup for the message). They are a `GoalSet` event (the PLAN panel shows them) and are put in the working model's context (`brief`), so it works towards them. A greeting gets none.
  - `check`, after the work: each criterion is marked met / not met / unknown against the record of what was done plus what the harness itself observed (`agent::Outcome`); a claim in the final answer that the record does not bear out is not "met". Shown as `CriteriaChecked` ("JUDGED" in the task's activity) and in the task's result line ("2 of 3 success criteria met").
  - `agreement`, plain code, no model: the user's response is compared with the criteria. All met and satisfied, or something not met and not satisfied, is agreement. All met but not satisfied means the criteria **missed the intent**; something not met but satisfied means they **asked too much**. Only unknowns is unclear and teaches nothing.
  - `learn_intent`, the learner, only when they disagree (`Live::weigh_criteria`, `learn_what_was_meant`): from the task, the criteria and how each stood, the answer and the response, a model says in one or two sentences what this user wants from this kind of task. It is kept as `Learned::Intent` (text starts `Intent:`), which lives by the same rules as any lesson (unconfirmed, confirmed or retired by later ratings and outcomes, capped, not stored twice) and is found by lookup when the next task of that kind has its criteria written. A response is a rating (`+`/`-`) or a **reply in the same task**: a reply is always put to the learner, which answers FINE, NEW (a new request) or an intent. When a rating alone does not show what was wanted, the timeline asks for a reply.
  - How often criteria judged a result the way the user did is counted (`tuning.json`, shown by `conscious tuning`). On by default; `--no-criteria` turns it off (it costs two small model calls a task). Not done: carrying on working by itself when a criterion is not met (the goal loop), and criteria for scheduled jobs being judged by anyone, since nobody responds to them.
- `src/web.rs` — reading the public web: one search (`search`: several independent sites tried in turn until one gives results (`ENGINES`: DuckDuckGo, DuckDuckGo Lite, Bing, then Wikipedia's search API), each read with a parser made for its page and, when that finds nothing on a page that did arrive, as plain outbound links (`parse_links`), so a site changing its markup degrades the results instead of ending research; which site answered and what went wrong on the way are reported. `CONSCIOUS_SEARCH_URL` (an address with `{q}`), if set, is tried first: the user's own search service, answering in SearXNG's JSON or as a page of links) and one page as text (`fetch`, `html_to_text`: headings become `#` lines; scripts, styles, navigation, header and footer are dropped; `<article>`/`<main>` is preferred). Network I/O only; it never decides whether it may run and never touches the knowledge store. Hard rules here: only `http`/`https` to hosts that resolve to public addresses (never this machine, a private network or a link-local address, checked again at every redirect, **and checked on the addresses the connection is actually made to** (`PublicOnly`, a resolver that refuses any non-public answer), so a name cannot answer "public" when checked and "this machine" when connected to), text only, at most 2 MB read and 40,000 characters kept, a generic client name and nothing about the user. No new dependency (`ureq`). The **`browse` tool** (`browse`, `Browsed`, `MAX_BROWSE_CHARS`) loads one address the user gave on the same checked-redirect fetch (`get_from`, which keeps the final address and the status) and returns title, main text cut at 20,000 characters with a note, final URL and HTTP status; it is a text fetch, not a rendering browser (no JavaScript), keeps nothing in the knowledge store, and its report says the text is data, never instructions. `check_address` is what can be refused with no lookup (scheme, user name, literal private/link-local/metadata addresses, `localhost`, `*.local`, `*.internal`): `Guard::check` denies `browse` on it in any mode, otherwise asks in careful mode and allows in trusted mode. It is dispatched in `agent.rs` through `research::Source::browse`, and sub-agents are offered it like the other read tools.
- `src/research.rs` — **knowledge research**, the `research` tool. The steps are fixed, not left to the model: (1) look in what earlier research kept (`RESEARCH_SPACE`); three or more direct matches answer it with no search unless `fresh` is asked for; (2) search for up to `MAX_QUERIES` (3) phrases, with secrets redacted from them; (3) read up to `MAX_PAGES` (3) of the best results and store each page's text in the knowledge graph under its own address, trusted only as `Trust::Inferred`; (4) return the passages that bear on the question, marked as outside reference data, never instructions. Every step is a `Research` event, and the task is `TaskState::Researching` meanwhile. Because what is read is kept, the same subject later is answered by the ordinary lookup with no search (seen in a real run). `Guard::check` makes `research` ask in careful mode (it sends search words out) and allows it in trusted mode. The web is behind the `Source` trait so the steps are tested without a network.
- `src/daemon.rs` — the **background process and the screen's connection to it**. The harness (conversation, agent loop, scheduler, timeline file) lives in one long-lived process; the TUI is a client. Plain `conscious` starts the daemon if none is running (`conscious daemon`, a hidden command, detached into its own process group, output to `daemon.log` in the data folder), then attaches. `q` only closes the screen.
  - *The data folder is the user's alone:* `bind` sets it to mode 0700, so no other account on the machine can read the conversation, memory or secrets in it, or reach the socket in the instant before it is set to 0600.
  - *Protocol:* one JSON object per line over a Unix socket (`ToDaemon`: `Attach`, `Command`, `Status`, `Schedule`, `Stop`; `ToClient`: `Hello`, `Event`, `Throughput`, `Draft`, `Status`, `Said`, `Closing`). The socket is `daemon.sock` in the data folder, mode 0600 (or, when that path is too long for a socket address, a file named by a hash of it in `$XDG_RUNTIME_DIR`). Nothing listens on the network. Only a connection that has attached may send a `Command`.
  - *One loop owns the harness* (`serve`): reader threads only hand messages to it. It polls `Live`, appends each event to the timeline, keeps the last `MAX_SINCE` (600) of this run, and sends it to every attached screen. Several screens may attach at once.
  - *Attaching* (`Hello`, `App::attach`): `before` is the timeline from earlier runs (history; `App::restore`), `since` is this run and is taken as true now, so a call waiting for approval is waiting on the new screen too. Memory is sent as the store holds it at that moment.
  - *Life of the process, all fixed rules:* one per data folder (a second start finds the socket taken and exits; a dead one's socket file is replaced). It ends by itself after `LINGER` (20 s) with no screen attached, nothing running or waiting to be remembered (`Live::settled`) and no job scheduled. `conscious stop` is refused mid-task without `--force`. A daemon left by an older build (`build_id`: version, file size and time) is replaced on the next start if it is idle with no screen; otherwise the screen attaches and says so.
  - *It keeps the folder and core model it was started with.* A screen started elsewhere, or with another `--model`, attaches and is told; changing either means `conscious stop` and starting again. `conscious schedule` asks the daemon when it is running, because the daemon holds the schedule in memory.
  - `--no-daemon` runs the harness inside the TUI process as before (`Feed::Live`); it ends when the screen is closed.
  - Not done: starting at login (a systemd user unit), so after a reboot nothing runs until `conscious` is started once; missed runs are then settled by each job's rule. A job that needs approval waits until a screen attaches and decides; there is no notification.
- `src/schedule.rs` — the **scheduler**: tasks set to start later by themselves. A job is a task in words plus a rule: `in 10m` / `at 09:00` / `at 2026-11-15 09:00` (once), `every 2h`, `daily 09:00` (local time), `when PATH changes` (a file or folder). Everything here is deterministic and takes the time as an argument (rule parsing, next due time, which job runs, missed runs); no model decides any of it. Kept in `schedule.json` beside the routing knowledge.
  - *Who sets jobs:* the agent, with the `schedule` tool (`create`, `list`, `pause`, `resume`, `cancel`). `Guard::check` makes `create` ask the user in careful mode and allows it in trusted mode; the rest is always allowed. Sub-agents are not offered the tool. The user can list and cancel with `conscious schedule [cancel ID]`.
  - *How a job runs:* a job is shown to the user as a **routine**. `Live::poll` starts the one due longest whenever a slot is free (`start_due_job`), as a branch (origin `routine #N`) in the same timeline, prefixed so the model knows nobody asked just now; its result is merged into main like any branch's. It passes through the same guardrails call by call; a call that needs approval waits in SIGNALS and holds later jobs until decided (one task at a time).
  - *Hard limits, compiled:* `MAX_JOBS` (20) and `MIN_EVERY` (a repeating job at most every 5 minutes). A repeating job's next time counts from its last start, so a late run is never followed by a burst of catch-up runs.
  - *Change triggers* (`When::Changed`): the path goes through `Guard::resolve`, so a job can only watch what the agent may read. `stamp` fingerprints it from sizes and modification times (a folder is walked, up to 2,000 entries, skipping `.git`, `target`, `node_modules`); `Live` looks every 5 s while nothing is running (`Schedule::watch`). No file-watching dependency. Such a job starts at most once per `MIN_EVERY`; changes in between count once. After its own run the stamp is taken again (`rebase`), so what the job changed itself does not set it off again.
  - *Missed runs:* jobs fire while the daemon is running. On start `Schedule::settle` applies each job's own rule: `run` (default: start once, however many runs were missed) or `skip` (wait for the next time; a one-off is dropped and the timeline says so). For a change trigger, `run` means a change made meanwhile sets it off and `skip` means it does not (`skip_unseen`).
  - *Daylight saving:* the UTC offset is read again every 10 minutes (`Schedule::set_offset`); daily jobs are re-timed to the new clock, and one whose time today has passed by the new clock without having run is made due at once.
  - Not done: triggers on a condition becoming true, priorities.
- `src/secrets.rs` — **the user's secrets, which never reach a model** (the user asked for this, 2026-11-14: keys must not go to the LLM, are typed in a separate window, and are handled properly). The whole design is that a model only ever knows a secret's *name*:
  - *Entry:* a window of its own on the screen (`App::secret_form`, `ui::render_secret_form`; `K` opens it, or it opens by itself when the agent asks with the `secret` tool). The value is drawn only as dots. It goes from the window to the store as `Command::Secret` (`secrets::Hidden`, whose `Debug` prints nothing), and is **never an event**: not in the timeline, the input line, a context or a log. `SecretAsked` / `SecretAnswered` carry the name only.
  - *Store:* `secrets.json` beside the routing knowledge, mode 0600, plain text (the protection of `~/.netrc`, no more). One store per process (`secrets::store`; in memory under test).
  - *Use:* the model writes `$NAME` in a shell command. `Guard::shell` puts the value in that command's environment and only the secrets the command names. `Guard::check` makes any such command **ask the user, at high risk, in every mode**: the model cannot see the value, but the command could send it anywhere. A command that names `secrets.json` is denied, and the file is hidden from sandboxed commands.
  - *Output:* `guard::redact` (which every tool result, and everything sent to Telegram, passes through) replaces any stored value with `[secret NAME]`. Values shorter than 6 characters are not looked for. A command that transforms the value (base64, reversing it) defeats this; that is why its use always asks.
  - *The agent's side:* the `secret` tool has `list` (names) and `request` (asks the user; blocks the task until they type it or decline, `Live::take_secret`). The system prompt tells it never to ask for a key in the conversation.
  - `conscious secrets` lists names; `conscious secrets remove NAME` forgets one. There is no command that takes a value: it would end up in a shell history.
  - Not done: an OS keyring; a secret the user pastes into the conversation by mistake is only caught if it looks like a known key format (`guard::redact`).
- `src/telegram.rs` — **a Telegram bot as a second way to reach main** (the user asked for it, 2026-11-14; it is the one channel, an exception to "no connectors" below). The token is the secret `TELEGRAM_BOT_TOKEN`; entering it connects the bot at once (`Live::telegram_follow`), and every later start connects it by itself. Rules, compiled, in `hear` (pure) and the bridge in `live.rs` (`Bridge`, `telegram_heard`, `telegram_tell`):
  - *Setting it up:* `conscious telegram` (`main::telegram_setup`), also offered once as the last, optional step of the first start: it says how to make a bot, reads the token from the terminal without echo (`read_hidden`; if echo cannot be switched off the token is not asked for), checks it with `getMe`, stores it as the secret, prints the bot's link and a pairing code, and waits up to 3 minutes for the user's account to send it. Entering the token with `K` in the TUI does the same, with the pairing line shown in the conversation (as a warning, since plain notices are not in ACTIVITY).
  - *The pairing code can always be found:* `conscious status` prints it while the bot is unpaired (`Live::telegram_state`, `Status::telegram`), and when anyone writes to an unpaired bot the code is said again in the conversation, at most once a minute (the user wrote to the bot, was told it was not paired, and could not find the code on the screen, 2026-11-15).
  - *The code cannot be guessed* (`PAIR_TRIES`, `tries_to_pair`): after 5 wrong codes the code is thrown away and pairing is locked until a new one is issued at the screen (a restart); the screen says so. An unpaired bot answers a stranger at most once a minute and not at all once locked. Whoever pairs controls an agent with a shell, and six digits could otherwise be tried one by one.
  - *One owner.* The timeline shows a six-digit code (`/pair CODE`); the account that sends it is the owner (`telegram.json`). Before that, and from anyone else after, nothing is passed on. Group chats are ignored.
  - *Messages:* the owner's messages are said to main (`Live::say`); main's replies and each merged branch result are sent back, cleaned by `guard::redact`.
  - *The phone gets a different reply from the screen* (the user asked, 2026-11-15): the screen keeps the reply as written, long and in markdown; Telegram gets it as plain text and as short as it can be (`live::for_phone`, prompt `telegram::FOR_PHONE`: the cheapest model rewrites it in at most five short sentences, keeping the outcome, numbers, names, paths and any question put to the reader; `telegram::plain` then takes out any markup left). A reply that is already one short plain paragraph (`already_brief`) goes as it is, with no call; if the model cannot be reached the reply goes with its markup taken out and nothing else changed. The rewriting runs off the feed's thread. It costs one small call per reply sent to Telegram.
  - *Errors reach the phone too* (the user asked, 2026-11-15): an `Alert` of severity error, such as a task stopped by a backend's usage limit, is sent to the owner as it stands, in plain text; otherwise a task that stopped would just fall silent there. The bridge's own `Telegram:` errors are not sent.
  - *Seen and typing* (the user asked, 2026-11-15): a message from the owner is marked as seen at once (`Bot::seen`: a bot cannot set Telegram's read ticks, so it reacts to the message with an eyes emoji), and "typing…" is shown for as long as anything is being worked on (`Bot::typing`, sent again every `TYPING_EVERY`, 4 s, by `Live::telegram_typing`). Neither is worth a warning when it cannot be sent.
  - *Approvals by button* (the user asked for this, 2026-11-14): a call that needs approval is sent with Approve and Deny buttons (`Bot::ask`, `telegram::decision`). The owner pressing one is `Command::Decide`, the same as `a` / `d` at the screen; the press is acknowledged and the message is rewritten to say what was decided and by whom, also when it was decided at the screen (`Bot::settle`, on the `ToolDecision` event). A button on a call that is no longer waiting, or pressed by anyone else, decides nothing. **Two kinds of call are decided at the screen only** (`telegram::SCREEN_ONLY`): `access` (widening what the agent may do) and `adopt self-update` (a change to the harness's own guardrails); the chat is told they are waiting, with no buttons. **A secret is never entered from Telegram.**
  - *Photos, video, audio, voice notes, files:* fetched with `getFile` (Telegram lets a bot fetch up to 20 MB, `MAX_FILE`), saved in the start folder under `telegram-inbox/` with a safe name (`telegram::file_name`), and main is told the kind, the path and the caption. **The models are given text only** (every provider is text in, text out), so main is told plainly that it cannot see or hear the file and must work on it with its tools. Seeing images and transcribing audio need a provider that takes them; that is not built. Nothing is sent *to* Telegram but text.
  - Long polling on a thread of its own (`getUpdates`, 25 s), sending on another; no new dependency (`ureq`). The token is never in an error (`Api::clean`). While a bot is connected the background process does not end by itself (`Live::connected`).
  - What main says leaves the machine for Telegram's servers; that is the user's choice in connecting a bot.
- `src/preflight.rs` — the **start-up checks**, run on every start and printed by `conscious check`. Two halves that must stay apart: `probe` looks at the machine (each installed CLI's own sign-in status command via `provider::cli::login`, the local server's model list, whether the data folder is writable, whether the sandbox works, whether there is a terminal) and `judge` turns those `Facts` into a report and the core model. `judge` is pure and total: same facts, same report, same core, and **no model is called to decide anything**. Core order with no model named: Claude Code signed in, Codex signed in, a local server's first model, then a CLI that would not say whether it is signed in. A named model is never swapped for another; if its backend is known not to work, the start stops with the reason and the fix (exit code 2). Missing extras (sandbox, data folder, terminal) are warnings, never a reason not to start, and appear once in the timeline. **The first start on a machine** (`main::first_run`, `Report::welcome`, `first_run_order`; the user asked for it, 2026-11-14) says in the terminal, before anything starts, that conscious brings no model and works through Claude Code or Codex (or a running local server, or a named OpenAI / OpenRouter model), prints the whole report, and sends one small real request to the chosen core to see that it answers; if it does not, the other ready backends are tried in a fixed order and the first to answer becomes the core. If none answers the start stops (exit code 2) with what to do. A marker (`first-run-checked` in the data folder) means it is done once. `check --call` is the only other part that sends a real request (one per ready backend); it catches what sign-in status cannot, such as a usage limit. The routing pool (`provider::available_models`) also leaves out a backend that says it is signed out.
- `install.sh` — builds a release binary and copies it to `~/.local/bin` (`PREFIX` overrides; `--uninstall` removes it, keeping data), then runs `conscious check`. It never uses sudo and never installs other software; it says what is missing and how to get it.
- `src/main.rs` — argument parsing, the `Feed` enum (demo, in-process live, or `Remote`: the daemon, which is the normal case), `screen` (start the daemon if needed, attach, say what is left running on exit), and the `ask` one-shot command.
- `src/agent.rs` — the **agent loop** for one task: ask the model, run the tools it asks for, hand back the results, repeat until it answers without a tool call. Hard limits are enforced here, not requested of the model, and are sized for hours of work (the user asked for that, 2026-11-14): `MAX_STEPS` (400 model calls per run), `TOKEN_BUDGET` (6M tokens per run), `MAX_TIME` (2 hours per run), and a stall check (the same call three times running). When a limit ends a run, the model is asked once more, with no tools, to say where things stand (`wrap_up`); that account is the task's reply, so replying "continue" in the same task carries on from it. A limit therefore ends a run, not the work. `Command::Stop` ends a run at its next step with no extra call. A malformed tool request is sent back to the model twice at most. Each step is an event (`ToolRequested` with the policy's reason, `ToolDecision`, `ToolFinished`, `PlanUpdated`), so the timeline shows what was done and why it was allowed. The loop also reads off **how the run went** from what it did (`Outcome`, via `Evidence`): `Verified` when it ended by itself with its last check (a test, build or lint command, `check_in`) passing and nothing changed after it; `Failed` when it was cut short or its last check failed; otherwise `Unknown`. A check only counts if its own result is the command's exit status: one piped into something or followed by another command does not. This is evidence, not the model's opinion of itself, and it is what lessons are judged by when the user does not rate (it does not feed routing, which still learns from the user's ratings only).
- **How the agent is told to behave** (`agent::system_prompt`; rewritten 2026-11-15 after the user showed it being "very unhelpful": listing open items, asking the same question in a loop, hedging, and refusing to write a script because its text said `sudo`). The user's words: "more autonomously goal driven, successful, somehow-do-it mindset", "I don't need problems, only solutions", "too much information". So the prompt says: decide and act; do what is in your power now and do not offer it; check things yourself and never ask the user to run a command to confirm; ask only for what only the user can give, never twice; what the user calls done is settled. **A denied call refuses that action, not the goal**: find another way within what is allowed, but never disguise the refused action. Replies are short, result first, solutions not problems, no recital of criteria (`goal::brief` no longer asks for one), no list of things still open, at most one question. Keep it that way: do not add wording that has the agent report what it did not verify or what remains.
  - *Handing work to the user* (`user_script` tool, `tools::save_user_script`): anything that needs root, or that the harness will not run, is written as a script in `<tmp>/conscious-scripts/` and the user is given the one line to run. The harness never runs such a script: `Guard::check` denies any command that names that folder, so it cannot be a way round the guardrails. `sudo` in a command is still refused; `sudo` in a script for the user is the point of the tool.
  - *Forgetting* (`forget` tool, `KnowledgeBase::forget`): a memory that is wrong is retired (kept on record, never found again), only when the lookup's best direct match is a note. Before this the agent could only add a correction beside a wrong memory.
- **Agent behaviours taken from Hermes Agent and OpenClaw** (2026-11-14; only how the agent acts, not their connectors or channels). All live in `src/agent.rs` unless noted:
  - *Self-written skills* (`src/skills.rs`): after a task with at least `SKILL_MIN_CALLS` (4) tool calls, the model that did it is asked what a future task should not have to work out again (`reflect`, prompt `skills::DISTILL`). It replies with one of three things: a **skill** (name, when-to-use line, steps), a **rule** or **know-how** (see "Two kinds of learned behaviour" under the knowledge store; saved as a note in memory, unconfirmed until a passing check or a rating backs it, labelled as the agent's own and whether it is confirmed), or `SKIP: <reason>`. It is shown the existing skills and what memory already holds on the task, so it does not write down what is already known (models skip a skill for anything they find obvious; the lesson is what keeps such work from being lost). Skills are Markdown files in `skills/` beside the routing knowledge. Each task is shown only the list (name + when); the agent loads one with the `skill` tool, and refines it by saving under the same name. The harness curates: a skill used in tasks rated bad twice (and more bad than good) is retired, and beyond 40 active the least useful are retired. The user's `+`/`-` rating of a task counts for the skills it loaded. The timeline always says what was kept, or the model's own reason for keeping nothing.
  - *Compaction inside a task* (`compact`): when a task's own messages pass `Limits::compact_at` (24k estimated tokens), all but the last `KEEP_RECENT` (6) are replaced by a summary from the cheapest model, cut so no tool result is separated from its call. If no summary can be had, the old steps become a bare list of the actions taken.
  - *Project instructions* (`project_instructions`): the start folder's `AGENTS.md` (else `CLAUDE.md`) is put in the model's context, below the harness's rules.
  - *Memory tools*: `recall` (a graph lookup the agent asks for mid-task) and `remember` (a note the agent chooses to save), alongside the automatic lookup and digest.
  - *Sub-agents* (`delegate`, offered to branches, not to main, which opens a branch instead): a fresh context with its own model choice (the sub-task is rated by itself), the same guardrails and approval path, its own agent id in the timeline, and its report returned as the tool result. One level only: a sub-agent is not offered `delegate` or `plan`, and **the loop refuses any call to a tool that was not offered**, whatever the model asks for.
  - Not taken: persona files and Hermes's offline fine-tuning. A heartbeat is a scheduled job (`src/schedule.rs`), run by the background process.
- `src/guard.rs` — the **guardrails**; every tool call passes `Guard::check` first. Verdicts: allow (reads inside the project; read-only shell commands; `cargo check|build|test|clippy|fmt` when a sandbox exists), ask the user (writing or editing files; any other shell command, flagged high risk if hard to undo or outward-facing such as `rm`, `git push`, `curl`), deny (paths outside the project, `.git` internals, `sudo`, piping into a shell, and similar). File tools cannot leave the project folder (`resolve` defeats `..` and symlinks). Shell commands run in a bubblewrap sandbox when available: filesystem read-only except the project, credential folders hidden, no network unless the user approved that very command. `redact` strips keys and private keys from all tool output. **Do not move any of this into prompts or into the interpreted policy.**
  - *Hardened after a security review (2026-11-15):* (1) **A read-only command that looks outside the allowed folders asks** (`Guard::reads_outside`), sandbox or not, in either mode: `cat ~/.bash_history` used to run unasked because `cat` only reads, although the file tools could never have read that file, and what it printed went to the model. System folders (`/usr`, `/bin`, `/lib`, `/etc`, `/opt`, `/sys`, `/tmp`) stay free to look at. (2) **A command is not handed this process's own keys** (`sensitive_env`): variables whose names say key, token, secret, password, credential, auth or cookie, and the harness's own `CONSCIOUS_*`, are removed from every command's environment, so `env` cannot print a model backend's API key; the secrets a command names are added after. (3) **What can carry text out is kept small or asked about**: a `browse` address with a query, a fragment or more than 120 characters asks even in trusted mode (`carries_data`), and a search phrase is cut at `research::MAX_QUERY_CHARS` (160). A model misled by a page it read could otherwise put the user's words into an address or a search. This narrows that way out; it does not close it (short phrases still leave). (4) The harness's data is recognised by its real paths (`.local/share/conscious`, `.config/conscious`, the protected folders), not by the word `conscious/`, which made every path in a project of that name ask.
- **Harness settings are tools, not files.** The agent cannot reach the harness's own data or config (they are outside the project folder, by design), so anything the user may ask it to change about the harness needs a tool. So far: `models` (`Router::manage_models`: list the pool, switch a model or provider off for N days or until told otherwise, switch it back on; stored as `banned` in the routing knowledge, never applies to the core). When a user request cannot be carried out because no such tool exists, add the tool rather than letting the model explain manual steps.
- **Access is granted by the user and remembered** (`guard::Access`, saved as `access.json` beside the routing knowledge). Two things can be widened: the folders the agent may work in (the start folder plus any added), and the mode. `careful` (the default): file changes and most commands ask. `trusted`: file changes and ordinary commands inside the allowed folders run without asking, relying on the sandbox (writes confined to those folders, no network). **Without a sandbox, trusted mode still runs ordinary commands without asking** (the user asked, 2026-11-14: "auto allow unless it is dangerous; file writes are ok, deletes are dangerous"), but then only the command's text can be judged, so more asks (`Guard::unconfined_danger`, `RISKY_UNCONFINED`): every way of deleting (`rm`, `rmdir`, `find -delete`/`-exec`, `git rm`, `shred`, `truncate`), anything that names the network or changes the machine, anything naming the harness's own data, anything using `~`, `$HOME`, `..`, `$(` or backticks, and any absolute path outside the allowed folders. This is a net with holes: a script the command runs can do what its text does not say. A working sandbox is the real protection. In both modes high-risk commands (`rm`, `git push`, network, installs) ask and forbidden ones are denied. The agent requests a change with the `access` tool, which always needs the user's approval in the TUI (high risk for adding a folder or turning on trusted mode); it can never grant itself anything, and neither should a coding agent working on this repo write that file for the user. System folders and the harness's own data can never be added, and the harness's data stays read-only inside the sandbox and unreachable by the file tools even if a parent folder is granted.
- `src/tools.rs` — the tools themselves and their JSON schemas. A tool does the work and reports; it never decides whether it may run. Output is redacted and clipped before it is returned.
- `src/timeline.rs` — the **persistent timeline**. Every event is appended to `timeline.jsonl` (beside the routing knowledge) the moment it happens and never rewritten. On start the most recent 400 are read back: `App::restore` rebuilds the screen from them (stamped with their clock time; stale status lines and index loads are skipped) and `Live::resume` puts the recorded conversation back into working memory. A restart therefore continues the last session. `EventKind` and everything in it must stay serialisable; unreadable lines (a torn write, an event kind from another version) are skipped, not fatal.
- `src/markdown.rs` — markdown → styled, width-wrapped terminal rows (headings, bold, italic, inline code, fenced code, lists, quotes, rules, links, tables). Used for model replies in the timeline and in the reply modal. User messages stay plain.
- `src/theme.rs` — palette (neon on near-black). Keep colours here, not inline.
- Visual language (in `ui.rs`): HUD frames via `hud()` (dim rule, bright corner brackets, slanted `chip()` title), segmented gauges, smooth braille area charts (`area_chart()` + `smooth()`: 2×4 dots per cell, Catmull-Rom between samples, sliding between samples so they scroll continuously; the screen redraws every 33 ms while state ticks every 80 ms), per-agent `pulse()`, and a dot-grid `texture()` post-pass. (A moving CRT scanline was removed: the user found it distracting. Do not add screen-wide motion.) New glyphs must be single-width and present in common terminal fonts (check with `fc-list ":charset=<hex>"`); avoid emoji-presentation characters such as `⏸`.
- `src/snapshot.rs` — offscreen render + interaction tests using `TestBackend`.

## What this is

In the user's words (2026-11-13): **"a self learning interpreter code changing harness which will work towards a goal given a task."** The learning (routing evidence, memory), the interpreted and self-rewritten policy, and the knowledge graph exist. The part that works towards a goal (the goal loop and its tools) does not yet, and is the next thing to build.

`conscious` is an agent harness written in Rust: the runtime that sits between a user and an LLM, driving the loop, executing tool calls, and managing context.

## Design thesis

Existing harnesses (OpenClaw, Hermes Agent) are the reference points *not* to copy wholesale: they are user-driven (every step waits on a message), split work across many sessions with separate contexts, and have grown bloated. `conscious` takes the opposite positions:

1. **Goal-driven, not message-driven.** The user sets a goal once; the harness owns pursuing it. A goal carries verifiable success criteria, a budget (time/tokens/cost), and constraints. The loop is plan → act → observe → evaluate → re-plan, and it stops only when criteria are verified, the budget runs out, or it is blocked on a decision only the user can make. Asking the user is an exception path, not the driver.
2. **One chat, one continuous timeline.** No separate sessions. (Branches are not sessions: main is the one conversation, every branch's events go into the same timeline and the same memory, a branch's result is merged back into main, and a tab is a view of that timeline filtered to one task.) Everything (all goals, sub-tasks, sub-agents) happens in a single persistent conversation. The model's context window is *not* the chat history: each step's context is assembled from the timeline plus memory (working set, retrieved long-term memory, compacted summaries). Sub-agents and parallel work appear inline in that same timeline.
3. **Observability through a rich TUI.** The TUI shows the full information stack, not just chat: the goal tree and status, the plan, the live event/tool-call stream, exactly what is in the model's context right now (with a per-section token breakdown), memory reads/writes, and cost/budget. Every step emits a typed event into an append-only log, which is the single source of truth for the TUI, replay, and debugging "why did it do that?".
4. **Mimic human cognition.** Separate working memory from long-term memory (episodic, semantic, procedural/skills); load context by attention/relevance rather than preloading; self-monitor (detect being stuck or looping, estimate confidence, know when to ask); reflect after a goal to record lessons.
5. **Knowledge it retrieves and builds (RAG).** A knowledge store the agent both reads from and writes to. Sources: ingested material (docs, repos, web pages) and the agent's own experience (results, reflections, lessons). Every entry keeps provenance (source, when, verified or inferred). Retrieval is hybrid (keyword + vector) with optional reranking. Reads and writes are events, so the TUI shows what was retrieved for each step and what was learned.
6. **Guardrails as layers, enforced by the harness, not the prompt.** Autonomy makes these mandatory:
   - Permission policy per tool call: allow / ask / deny rules, with protected paths and commands.
   - OS-level sandbox for shell commands (filesystem and network limits), so policy mistakes are contained.
   - Hard budgets (tokens, cost, time, step count) and loop/stall detection.
   - Irreversible or outward-facing actions (deleting, pushing, sending) need confirmation unless the goal explicitly grants them.
   - Tool output, retrieved knowledge and MCP results are treated as untrusted data, never as instructions.
   - Secrets are redacted from context, logs and the TUI.
7. **Local-first default model.** Out of the box it runs a small local model on CPU (default: Gemma 4 E4B, quantized GGUF) so it works with no API key. Hosted models (e.g. Claude via an API key) plug in through the same provider layer. Expect the small model to be slow (single-digit tokens/sec on CPU) and weaker at tool calling, so: keep assembled context lean, validate every tool call against its schema before running it, and allow routing hard steps (planning, verification) to a stronger model when one is configured.
8. **Task scheduling.** Goals can be started by a schedule instead of the user: one-shot ("at 9:00 tomorrow"), recurring (cron/interval), or event-triggered (file change, a condition becoming true). Scheduled runs post into the same single timeline. Consequences:
   - The core runs as a background daemon so schedules fire with the TUI closed; the TUI is a client that attaches to it.
   - Unattended runs cannot wait on the user: when one hits an "ask" guardrail it pauses that goal and queues the question in the timeline, rather than guessing or proceeding.
   - Schedules persist across restarts, with an explicit policy for runs missed while the machine was off (skip, run once, or catch up).
   - A run queue with priorities and concurrency limits, since a local CPU model can realistically serve one goal at a time.
9. **Small core.** The core is the goal loop, event log, context assembly, memory/knowledge, guardrails, and a minimal tool set. Integrations, channels, and extras live outside the core. (One channel exists because the user asked for it: a Telegram bot, `src/telegram.rs`.)

## Capabilities (planned)

- **Shell (bash):** run commands in the working directory, sandboxed, with streamed output and timeouts.
- **Files:** read, write, edit, search (glob/grep).
- **MCP client:** connect to MCP servers (stdio and HTTP) and expose their tools, resources and prompts through the same permission policy as built-in tools.
- **Knowledge:** ingest, search, and write to the knowledge store.
- **Web:** search and fetch. (Exists as the `research` tool, `src/web.rs` + `src/research.rs`: it searches, reads and keeps. One given address is loaded as text by the `browse` tool, also in `src/web.rs`. There is no tool for posting anything and no JavaScript-rendering browser.)
- **Sub-agents:** spawn focused workers whose activity appears inline in the one timeline.
- **Scheduling:** the agent (and the user) can create, list, pause and cancel scheduled goals.

Open question: whether "mimic human ability" also includes computer use (seeing the screen, mouse/keyboard), or only cognition. Resolve with the user before designing for it.

## Stack

- Language: Rust (stable toolchain), built with Cargo. The dev profile optimises dependencies fully and our code lightly (`Cargo.toml`), so plain `cargo run` renders a frame in about 1.3 ms instead of 9.6 ms.
- Adopted: `ratatui` 0.30 for the TUI. Use its re-exported `ratatui::crossterm` rather than adding `crossterm` directly, so versions can't drift.
- Adopted: `rhai` 1 (feature `sync`) as the embedded interpreter for the decision policy. Pure Rust, sandboxed.
- Adopted (the user agreed, 2026-11-14): `fastembed` 7 for local text embeddings, with `default-features = false` and `hf-hub-rustls-tls`, `ort-download-binaries-rustls-tls`, `onnx` (rustls, like the rest; no system OpenSSL). It brings in ONNX Runtime, whose library is downloaded at build time, so the first build needs the network and takes a few minutes.
- Adopted: `ureq` 3 (blocking HTTP, rustls) for model APIs, with `serde` and `serde_json`. Model calls run on worker threads; there is no async runtime yet. Revisit when the daemon lands.
- Likely candidates, not yet adopted: `tokio` for async, `tracing` for structured events, `rmcp` (official Rust MCP SDK) for MCP, `tantivy` for keyword search, and a vector store such as `lancedb` or SQLite with `sqlite-vec` (vectors are a flat file searched by brute force today, which is fine into the tens of thousands of passages).
- Everything else (storage, embeddings) is **not yet decided**. Don't add a dependency for one of these without the user agreeing to it; once chosen, record it here.

## Commands

**One command starts everything; keep it that way.** The user asked for a single run command with nothing to set up first. Plain `cargo run` (or `conscious`) must: start the background process if it is not running and attach to it (the user never starts the daemon by hand), check the machine and pick a core model itself (`preflight`: the first backend that is ready: Claude Code signed in, else Codex signed in, else a running local server), sync the project in the current folder into the knowledge graph (`knowledge::cli::sync_project`: incremental, only if the folder has a project marker, capped at 1,500 files, into a space named after the folder, dropping documents whose files are gone), look every message up in the graph, remember every exchange, route by complexity, and learn from ratings. New features must switch themselves on by default; do not add a setup step or a required flag. Opt-outs exist: `--no-route`, `--no-knowledge`, `--demo`.

```sh
cargo run                                     # THE run command: everything on (needs a real terminal; q quits)
cargo run -- --model SPEC                     # same, with a chosen core model; CONSCIOUS_MODEL sets a default
cargo run -- --demo                           # the scripted demo, no model
cargo run -- ask --model SPEC "prompt"        # one-shot prompt, no TUI; quickest way to check a backend
cargo run -- models --model claude-code       # the pool, each family's tier and learned success estimate per complexity
cargo run -- feedback good|bad                # rate the last `ask` answer; routing learns from it
cargo run -- knowledge ingest PATH... [--space S]   # add files/folders to the knowledge graph (re-run to update)
cargo run -- knowledge search "query" [--hops N --trust verified --space S --budget N]
cargo run -- knowledge add "note with \`terms\`"     # remember something; knowledge stats shows the store
./install.sh                                  # build, install the `conscious` command, run the checks
cargo run -- check                            # what this machine has and which model would be the core (no model call)
cargo run -- check --call                     # the same, plus one real request to each ready backend
cargo run -- schedule                         # the jobs the agent has set to start by themselves
cargo run -- schedule cancel ID               # remove one
cargo run -- status                           # whether the background process is running: folder, core, task, screens, jobs
cargo run -- stop [--force]                   # end it (--force: even mid-task)
cargo run -- --no-daemon                      # everything inside this window only; ends when you quit
cargo run -- --no-semantic                    # lookups by words and links only, without the local embedding model
cargo run -- --no-criteria                    # no success criteria per task (saves two small model calls a task)
cargo run -- --no-self-update                 # never let it change its own source code
cargo run -- selfupdate                       # what it has tried to change in its own code, and what came of each
cargo run -- selfupdate rollback              # take the newest adopted change to its own code back
cargo test -- --ignored real_embed            # opt-in: loads the real embedding model (downloads it the first time)
cargo test -- --ignored real_web              # opt-in: asks each real search site once
cargo run -- telegram                         # connect a Telegram bot: its token (typed unseen), then pairing
cargo run -- secrets                          # the names of the secrets you have stored (enter one with K in the TUI)
cargo run -- secrets remove NAME              # forget one
cargo run -- skills                           # the procedures the agent has written for itself
cargo run -- lessons                          # the lessons it has drawn: confirmed or not, given to how many tasks, rated how
cargo run -- tuning                           # the learned limits: what each is now, its bounds, the evidence, and why it moved
cargo run -- policy                           # active policy version, history, rejected rewrites
cargo run -- policy show|rollback             # print the active script / step back one version
cargo run -- policy propose FILE              # put a script through the regression gate
cargo run -- policy review --model SPEC       # have the core review the policy now
cargo run -- ask --no-route --model SPEC "…"  # skip routing; everything goes to the core
cargo run -- --help                           # lists backends: claude-code, codex, openai:M, openrouter:M, local[:M]
cargo test -- --ignored real_claude           # opt-in test that calls the real claude CLI
SNAPSHOT_HTML=1 cargo test                    # also writes rendered frames to target/snapshots/*.{txt,html}
cargo build                                   # build
cargo test                                    # all tests
cargo test <name>                             # tests whose name contains <name>
cargo test <path::to::test> -- --exact        # one specific test
cargo test -p <crate>                         # one crate (if a workspace)
cargo fmt                                     # format
cargo clippy --all-targets -- -D warnings     # lint; treat warnings as errors
```

Backend environment: `OPENAI_API_KEY` (+ `OPENAI_BASE_URL`), `OPENROUTER_API_KEY`, `CONSCIOUS_LOCAL_URL` (default `http://127.0.0.1:8080/v1`), and `CONSCIOUS_CONTEXT` to override the per-backend context-window default.

After rebuilding, a daemon from the old build may still be running. A start replaces it only when it is idle with no screen attached; when testing by hand, `conscious stop` first (or use a scratch `CONSCIOUS_KNOWLEDGE_FILE`, which gives a separate daemon).

A test that loops forever while allocating will freeze the whole machine (it has happened). When running anything unproven, cap it: `(ulimit -v 6000000; cargo test)`.

Before considering a change done, it should pass `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and `cargo test`.

## Architecture

Planned. Nothing is fixed yet; document the real layout here as it forms. Concerns to keep separate:

- **Goal engine** (the act-observe loop exists in `src/agent.rs`; criteria and verification do not): goals with success criteria, budgets and constraints; the plan → act → observe → evaluate loop; verification and stop conditions.
- **Event log**: append-only, typed events for every step. The TUI, replay and debugging read from it; nothing else is the source of truth.
- **Context assembly**: builds each model call's context from the single timeline plus memory, within a token budget, and records what was included and why.
- **Memory & knowledge** (knowledge store implemented in `src/knowledge/`, see above; memory still planned): working memory vs. long-term (episodic, semantic, procedural); the RAG store (ingest, chunk, embed, hybrid retrieve, write back with provenance); post-goal reflection.
- **Guardrails** (implemented in `src/guard.rs` and the limits in `src/agent.rs`): permission policy, sandbox, budgets, loop detection, secret redaction. Every tool call passes through this layer before execution; tools never bypass it.
- **Model provider layer** (implemented, `src/provider/`): one trait over all backends: OpenAI-compatible HTTP (OpenAI, OpenRouter, local `llama-server` / Ollama) and the Claude Code and Codex CLIs in model-only mode. Per-task routing (complexity rating by the core, model choice by learned knowledge) is implemented in `src/router.rs`, `src/learn.rs` and `src/policy.rs`. Still planned: in-process inference for a single binary, a direct Anthropic API backend, and routing by step type (planning, verification) once the goal loop exists.
- **Tools** (shell and files implemented in `src/tools.rs`; web, knowledge, sub-agents and the MCP client still planned): all share one schema and one permission path.
- **Scheduler** (implemented in `src/schedule.rs`: one-shot, recurring and file-change triggers, missed-run rule, one task at a time; priorities and condition triggers still planned): persistent triggers; a run queue with priorities and concurrency limits; missed-run policy.
- **Daemon / client split** (implemented, `src/daemon.rs`): the core (agent loop, scheduler, event log) runs as a long-lived daemon; the TUI connects to it over a local socket and renders the event log and live state. The TUI never owns state, so the core stays testable without it.
